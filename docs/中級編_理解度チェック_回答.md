### Q1. セッション認証とトークン認証

> 「セッション認証」と「トークン（JWT）認証」の違いを説明してください。
> 
> 
> また、このアプリでJWTを採用した理由（利点）も述べてください。
> 

**回答:**

セッション認証は、サーバー側でログイン状態を管理し、ブラウザ側にはセッションIDのみを保持する認証方式である。

一方、JWT認証は、ユーザー情報を含むトークンをクライアント側で保持し、サーバーはトークンの署名や有効期限を検証することで認証を行う。

JWT認証はサーバー側でセッション状態を持つ必要がなく、API通信との相性が良いため、React や Next.js を使用した SPA 構成に適しているという利点がある。

そのため、このアプリでは JWT 認証を採用した。

### Q2. アクセストークンとリフレッシュトークン

> 以下について説明してください：
> 
- なぜトークンを2種類に分けるのか
- アクセストークンの有効期限が短い理由

（アクセストークン: 15分 / リフレッシュトークン: 7日）

**回答:**

アクセストークンは、API へアクセスする際に提示する短命のトークンである。これが切れるたびにログインし直すのはユーザーにとって負担が大きい。

そこで、有効期限の長いリフレッシュトークンを別に発行し、アクセストークンが切れてもリフレッシュトークンが有効であれば、再ログインなしでアクセストークンを再発行できるようにしている。

アクセストークンの有効期限を短くするのは、万が一トークンが漏洩した場合でも、不正利用できる時間を最小限に抑えるためである。

### Q3. パスワードのハッシュ化

> 「ハッシュ化」と「暗号化」の違いを説明してください。
> 
> 
> また、なぜパスワード保存にハッシュ化を使うのか述べてください。
> 

**回答:**

暗号化は、鍵を使って元のデータに戻せるようにする技術である。

一方、ハッシュ化は元に戻せない一方向の変換を行う技術である。

パスワード保存では、ログイン時に同じハッシュ値になるかを確認できればよく、元のパスワードそのものを保存する必要がない。

そのため、DB 流出時の被害を減らす目的で、パスワードはハッシュ化して保存する。

### Q4. 認可（Authorization）

> 「認証」と「認可」の違いを説明し、
> 
> 
> 「自分の投稿のみ編集・削除できる」機能がどちらに該当するか答えてください。
> 

**回答:**

認証（Authentication）とは、ログイン時にユーザー本人かどうかを確認することであり、JWT 認証などを用いてログイン済みかを確認する。

認可（Authorization）とは、認証済みユーザーがどの操作を許可されているかを確認することである。

「自分の投稿のみ編集・削除できる」機能は、他人の投稿を操作できないよう権限を確認しているため、認可に該当する。

### Q5. CORS設定の実務理解

> 以下について説明してください：
> 
- 本番環境でのCORS設定の変更点
- `allowedOrigins("*")`の問題点

**回答:**

本番環境では、localhost ではなく実際のフロントエンドの URL のみを `allowedOrigins` に設定し、決められた Origin からのみ API アクセスを許可する必要がある。

`allowedOrigins("*")` を設定すると、すべての Origin からのアクセスを許可してしまうため、悪意あるサイトからの API 通信も許可される可能性があり、セキュリティ上問題がある。

---

### Q6. SQLインジェクション

> SQLインジェクションとは何か説明してください。
> 
> 
> また、MyBatisで防ぐための実装上の注意点を述べてください。
> 

**回答:**

SQL インジェクションとは、入力欄へ不正な SQL 文を混ぜ込み、意図しない SQL を実行させる攻撃である。

例えば、WHERE 句を書き換えて不正ログインや情報取得を行う危険がある。

MyBatis では、`${}` ではなく `#{}` を使用して PreparedStatement として値をバインドすることで、入力値を SQL 文として解釈させず、SQL インジェクションを防ぐことができる。

---

### Q7. XSS（クロスサイトスクリプティング）

> 以下について説明してください：
> 
- `<script>alert('攻撃')</script>` が投稿された場合のリスク
- Reactでの対策方法

**回答:**

`<script>alert('攻撃')</script>` が投稿された場合、ブラウザがそれを JavaScript として実行してしまい、JWT や Cookie の取得、不正操作などが行われる危険がある。

React では、JSX で `{ }` を使って値を表示する際に自動でエスケープ処理が行われるため、script タグをコードではなく単なる文字列として扱い、XSS を防ぐことができる。

---

### Q8. HTTPSと本番セキュリティ

> 以下について説明してください：
> 
- ALBを使った場合のSSL/TLS証明書の配置場所
- ALB〜バックエンド間通信のHTTPS必要性

**回答:**

ALB を使った場合、SSL/TLS 証明書は ALB に配置する。

ALB〜バックエンド間通信でも HTTPS が望ましい理由は、暗号化されていない場合、送信されるデータが第三者に盗み見られたり改ざんされたりする危険があるためである。VPC 内部であっても、機密性の高い通信は暗号化しておくことが安全である。

## 🏗 第2章: アプリケーションアーキテクチャ（7問）

### Q9. レイヤードアーキテクチャ

> Controller / Service / Repository の役割を説明してください。
> 
> 
> また、以下も答えてください：
> 
- なぜ分離するのか
- ControllerとServiceの責務の境界

**回答:**

Controller は、HTTP リクエストを受け取り、Service を呼び出してレスポンスを返す役割を持つ。

Service は、業務ロジックやデータ加工などの処理を行う。

Repository は、DB へのアクセスを担当し、データの取得や保存を行う。

レイヤーを分離することで、役割が明確になり、保守性や可読性を高めることができる。

責務の境界としては、Controller はリクエスト受付やレスポンス返却（入出力の窓口）を担当し、Service は実際の業務処理（ビジネスロジック）を担当する。Controller には業務ロジックを書かない、というのが境界の目安となる。

---

### Q10. DTOパターン

> エンティティを直接APIに使わない理由を説明してください。
> 

**回答:**

Entity は DB テーブルに対応するオブジェクトであり、DB の情報をそのまま持っている。

一方 DTO は、API やレイヤー間でデータの受け渡しを行うためのオブジェクトである。

Entity を直接 API に使用すると、password など公開すべきでない情報まで外部に出てしまう危険がある。

そのため、API で必要な項目のみを持つ DTO を使用し、セキュリティの確保と責務分離を行う。

---

### Q11. グローバル例外ハンドリング

> 各Controllerでtry-catchする場合と比較した利点を説明してください。
> 

**回答:**

グローバル例外ハンドリングとは、アプリ全体の例外処理を 1 箇所でまとめて管理する仕組みである。

各 Controller で try-catch を書く場合、同じようなエラー処理が重複し、保守性が低下する。

グローバル例外ハンドリングを使用することで、エラー処理を共通化でき、レスポンス形式の統一や保守性向上につながる。

---

### Q12. MyBatis vs JPA

> 以下の観点で違いを説明してください：
> 
- SQL制御
- 学習コスト

**回答:**

MyBatis は、SQL を自分で記述するため、細かく SQL を制御できる特徴がある。その反面、SQL の知識が必要であり、記述量も増えやすい。

一方 JPA は、Java オブジェクトを操作することで SQL を自動生成できるため、CRUD 処理を簡単に実装できる。ただし、内部動作が複雑で、Entity 管理や N+1 問題など JPA 特有の理解が必要になる。

---

### Q13. 環境ごとの設定管理

> プロファイルの仕組みと、環境ごとに設定を分ける理由を説明してください。
> 

**回答:**

プロファイルとは、環境ごとに異なる設定を切り替えるための仕組みである。

Spring Boot では、`application-local.yml` や `application-prod.yml` などを用いて、環境ごとの設定を管理できる。

例えば、DB 接続先や API の URL、JWT 秘密鍵などは、開発環境と本番環境で異なるため、設定を分離する必要がある。

これにより、安全性や保守性を向上できる。

---

### Q14. Flyway（DBマイグレーション）

> マイグレーションツールを使う理由を説明してください。
> 
> 
> （直接ALTER TABLEしない理由）
> 

**回答:**

Flyway は DB の構造変更履歴を管理するツールである。

テーブルに列を追加するなどの変更を直接 ALTER TABLE で実行すると、環境ごとの差異が生まれやすく、変更履歴の管理も難しくなる。

そのため Flyway を利用し、DB 変更を SQL ファイルとしてバージョン管理することで、どの環境でも同じ手順で確実に変更を適用できるようにする。

### Q15. Axiosインターセプター

> インターセプターとは何か説明してください。
> 
> 
> また、これが無い場合の問題点も述べてください。
> 

**回答:**

Axios は JavaScript から API 通信を行うためのライブラリである。

インターセプターは、API 通信の送信前や受信後に共通処理を実行する仕組みである。

例えば、JWT トークンの自動付与や、401 エラー発生時のログイン画面への遷移などを実装できる。

インターセプターが無い場合、各 API 呼び出しごとに同じ処理を書く必要があり、コードの重複や保守性の低下につながる。

### Q16. React Context

> なぜpropsではなくContextが選ばれたのか説明してください。
> 
> 
> また、適切なケース / 不適切なケースも述べてください。
> 

**回答:**

props は親コンポーネントから子コンポーネントへデータを渡す仕組みである。

しかし階層が深くなると、中間コンポーネントを経由してデータを渡し続ける必要がある（props drilling）。

Context はアプリ全体で共有するデータを直接取得できる仕組みであり、props drilling を防ぐために利用される。

適切なケースは、ログインユーザー情報やテーマ設定など、複数の画面で利用する共通データである。

不適切なケースは、特定の画面だけで利用するローカルな状態である。これらまで Context に入れると、かえって見通しが悪くなる。

---

### Q17. カスタムフック

> なぜロジックをコンポーネントではなくフックに分離するのか説明してください。
> 

**回答:**

コンポーネントは画面表示を担当する部品である。

カスタムフックは、状態管理や API 通信などのロジックを共通化するための仕組みである。

ロジックをコンポーネントから分離することで、コードの見通しが良くなり、再利用性や保守性が向上する。

また、コンポーネントは画面表示、カスタムフックは処理を担当することで、責務を分離できる。

### Q20. SPAルーティング

> 従来のWebとの違いを説明し、
> 
> 
> 「直接URLで404になる問題」の原因と対策を述べてください。
> 

**回答:**

SPA（Single Page Application）は、最初に 1 つの HTML を読み込み、JavaScript によって画面を切り替える方式である。

従来の Web アプリでは、画面遷移ごとにサーバーから新しい HTML を取得していた。

SPA では画面遷移をフロントエンド側で管理するため、特定のパスに直接 URL でアクセスすると、サーバーがそのパスを認識できず 404 エラーになる場合がある。

対策として、サーバー側で全てのリクエストを index.html へ転送（フォールバック）し、React 側でルーティングを処理するように設定する。

### Q21. 楽観的UI更新

> 以下を比較してください：
> 
- サーバー応答後に更新
- 楽観的更新

そしてどちらが適切か理由付きで答えてください。

**回答:**

サーバー応答後更新は、API 処理が成功したことを確認してから画面を更新する方式である。正確性が高いが、通信完了まで待つためユーザーには遅く感じることがある。

楽観的更新は、API の成功を前提として先に画面を更新する方式である。ユーザー体験は向上するが、失敗時には画面状態を元に戻す処理が必要となる。

いいね機能などでは楽観的更新が適しているが、金額や契約情報など重要なデータ更新ではサーバー応答後更新の方が適切である。

## ☁️ 第4章: インフラとデプロイ（5問）

### Q22. Docker / docker-compose

> Dockerの概要と、ローカルインストールとの違いを説明してください。
> 

**回答:**

Docker は、アプリケーションの実行環境をコンテナとしてまとめる技術である。これにより、異なる PC でも同じ環境を再現できる。

ローカルインストールでは、各 PC へ直接 Java や DB をインストールするため、環境差異が発生しやすい。

一方 Docker では、必要な環境をコンテナにまとめるため、開発環境を統一しやすい。

また、docker-compose は、複数のコンテナをまとめて管理・起動するための仕組みである。

---

### Q23. AWS基本サービス

> EC2 / RDS / ALB / S3 の役割と分離理由を説明してください。
> 

**回答:**

EC2 は、アプリケーションを実行するための仮想サーバーである。

RDS は、データベースを管理するサービスであり、アプリケーションのデータを保存する。

ALB は、ユーザーからの通信を受け付け、適切なサーバーへ振り分けるロードバランサである。

S3 は、画像やファイルなどを保存するストレージサービスである。

これらを分離することで、役割を明確にし、スケーラビリティや保守性を向上できる。

---

### Q24. IaC（Terraform）

> 手動構築との違いとメリットを説明してください。
> 

**回答:**

IaC（Infrastructure as Code）とは、インフラ構成をコードで管理する考え方である。

Terraform を利用することで、EC2 や RDS などの AWS リソースをコードで定義し、自動構築できる。

手動構築では、管理画面から設定を行うため、設定漏れや環境差異が発生しやすい。

一方 Terraform では、構成をコードとして保存できるため、再現性や保守性が向上し、同じ環境を簡単に構築できる。

---

### Q25. 環境変数と機密情報

> ソースコードに直接書く問題点と、安全な管理方法を説明してください。
> 

**回答:**

機密情報をソースコードへ直接記述すると、GitHub などへ公開された際に第三者へ漏洩する危険がある。

例えば AWS のアクセスキーが漏洩すると、不正利用や高額請求につながる可能性がある。

そのため、機密情報は環境変数や Secrets Manager などで管理し、ソースコードへ含めないようにする。

また、`.env` ファイルを `.gitignore` へ追加し、Git の管理対象外とすることで情報漏洩を防ぐことができる。

---

### Q26. 構造化ログ

> JSONログの利点と、MDC（requestId / userId）の役割を説明してください。
> 

**回答:**

構造化ログとは、ログを JSON 形式などで出力し、検索や分析をしやすくしたログである。

JSON ログにすることで、ユーザー ID やログレベルなどを項目ごとに管理でき、ログ基盤での検索・集計が容易になる。

MDC はログへ共通情報を付与する仕組みであり、requestId や userId を自動的に出力できる。

requestId は 1 回のリクエストを追跡するために利用し、userId はどのユーザーの操作かを識別するために利用する。

## 🧪 第5章: テストと品質保証（5問）

### Q27. テストの種類

> 以下の違いと具体例を説明してください：
> 
- 単体テスト
- 結合テスト
- E2Eテスト

**回答:**

**単体テスト:**
クラスやメソッド単位で動作確認するテスト。if 文の分岐や計算処理などを確認する。

**結合テスト:**
複数のモジュールやシステムを連携させて、正しく動作するか確認するテスト。
例：Controller → Service → Repository → DB の連携。

**E2E テスト:**
利用者目線でシステム全体の動作を確認するテスト。
例：ログインから登録完了までの一連の流れを確認する。

---

### Q28. モック（テストダブル）

> モックの利点と注意点を説明してください。
> 

**回答:**

モックとは、テスト時に本物の DB や外部 API の代わりに使用する偽物のオブジェクトである。

モックを利用することで、外部環境に依存せず、高速かつ安定して単体テストを実施できる。

一方で、モックは本物の動作を完全には再現できないため、モックでは成功しても実際の環境では失敗する可能性がある。

そのため、モックを使った単体テストだけでなく、結合テストも実施することが重要である。

---

### Q29. 境界値とエッジケース

> 「1〜280文字制約」のテストケースを境界値分析で説明してください。
> 

**回答:**

境界値分析では、有効範囲の境界付近を重点的にテストする。

1〜280 文字制約の場合、

- 0 文字（エラー）
- 1 文字（OK）
- 2 文字（OK）
- 279 文字（OK）
- 280 文字（OK）
- 281 文字（エラー）

を確認する。

またエッジケースとして、空文字、空白のみ、改行のみ、絵文字や全角文字なども確認する。

### Q30. テストカバレッジ

> カバレッジの意味と限界を説明してください。
> 
> 
> 「100%＝バグなし」は正しいかも答えてください。
> 

**回答:**

テストカバレッジとは、プログラムコードのうち、どれだけテストで実行されたかを示す指標である。

カバレッジが高いほど、多くのコードがテストされていることを意味する。

しかし、カバレッジが 100% であっても、全ての入力値や業務パターンを確認できているとは限らない。

そのため、「カバレッジ 100% = バグなし」は正しくない。

カバレッジは品質を測る指標の一つであるが、バグが存在しないことを保証するものではない。

### Q31. フロントエンドテスト戦略

> Testing Libraryの思想と、その利点を説明してください。
> 

**回答:**

Testing Library は、ユーザーの操作に近い形で画面をテストすることを重視したテストライブラリである。

内部実装ではなく、ユーザーが実際に見るテキストやボタン操作を基準にテストを行う。

これにより、実際の利用状況に近いテストができ、内部実装の変更による影響を受けにくくなる。

そのため、保守性が高く、信頼性の高いフロントエンドテストを実現できる。

## 🧭 第6章: 設計原則と実務判断（5問）

### Q32. N+1問題

> 概念と、タイムライン例で説明してください。
> 

**回答:**

N+1 問題とは、一覧取得後に各データごとに追加 SQL を実行してしまい、SQL の発行回数が増加する問題である。

例えばタイムライン表示で、投稿一覧を取得した後、各投稿のユーザー情報を 1 件ずつ取得すると、

投稿取得 1 回 + ユーザー取得 N 回

となり、合計で N+1 回の SQL が実行される。

これにより性能低下が発生するため、JOIN などを利用してまとめて取得することで改善できる。

### Q33. ページネーション

> 必要な理由と、代表的な2方式を比較してください。
> 

**回答:**

ページネーションとは、大量のデータを複数ページに分割して表示する仕組みである。

必要な理由は、表示速度の向上や通信量の削減、画面の見やすさ向上のためである。

代表的な方式として Offset 方式と Cursor 方式がある。

Offset 方式は実装が簡単でページ番号の指定がしやすいが、後ろのページほど処理が重くなる。

Cursor 方式は高速だが、特定ページへ直接移動しにくいという特徴がある。

---

### Q34. 画像アップロード設計

> DB保存とS3保存の違いと利点を説明してください。
> 

**回答:**

画像を DB 保存する場合は、画像データそのものをデータベースへ保存する。管理はしやすいが、データベースの容量が増加し、性能低下の原因となる。

一方 S3 保存では、画像は S3 へ保存し、DB には画像の URL のみを保存する。S3 は大量の画像やファイル保存に適しており、DB の負荷を軽減できる。

そのため、実務では画像や PDF などのファイルは S3 へ保存し、DB には参照情報のみを保持することが多い。

### Q35. APIバージョニング

> 代表的な方式と特徴を説明してください。
> 

**回答:**

API バージョニングとは、API の仕様変更時に古い利用者との互換性を維持するため、API にバージョンを付けて管理する仕組みである。

代表的な方式として、

- **URL 方式**
  `/api/v1/users` / `/api/v2/users`
- **Header 方式**
  Version ヘッダーで指定
- **Query Parameter 方式**
  `?version=v1`

などがある。

URL 方式は分かりやすく管理しやすいため、実務でよく利用される。

### Q36. 技術選定

> 判断基準を説明し、
> 
> 
> React + Spring Boot + PostgreSQL を例に具体化してください。
> 

**回答:**

技術選定では、作りたい機能に合っているか、学習コスト、情報量、保守性、チームで扱いやすいかなどを基準に判断する。

React は画面をコンポーネントとして分割でき、SPA 開発に向いている。また利用者が多く情報も豊富である。

Spring Boot は Java で Web API を開発しやすく、認証や DB 接続、レイヤードアーキテクチャを構成しやすい。

PostgreSQL は信頼性の高い RDB であり、ユーザー情報や投稿データなどを安全に保存できる。

この構成は、フロントエンド、バックエンド、データベースの役割を分離でき、Web アプリ開発に適している。
