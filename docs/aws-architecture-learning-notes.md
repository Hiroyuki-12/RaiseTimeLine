## なぜ EC2 無しにできるのか

旧構成は EC2 を 1 台借り、その中に Nginx（フロント配信）と Spring Boot（バックエンド）を同居させ、OS もプロセスも
すべて自分で管理していた。EC2 がやっていた仕事は大きく 2 つ。これを別サービスに肩代わりさせると EC2 が要らなくなる。

| EC2 がやっていた仕事 | 置き換え先 | なぜサーバー管理が要らなくなるか |
|---|---|---|
| ① React（フロント）の配信 | S3 + CloudFront | React のビルド成果物は静的ファイル（HTML/JS/CSS）。「実行」ではなく「配布」なので常駐サーバーが不要 |
| ② Spring Boot（バックエンド）の実行 | ECS Fargate | 実行場所は要るが、それが「自分で OS 管理する EC2」である必要はない。コンテナだけを動かす |
| （DB） | RDS | データ保管・パッチ・バックアップを AWS に委譲 |

要点:

1. **フロントは「実行」ではなく「配布」なのでサーバー自体が不要** → S3 + CloudFront
2. **バックエンドは実行が必要だが "EC2 という管理対象" を Fargate に肩代わりさせられる** → コンテナだけ動かす

→ 「アプリは全部動いているのに、EC2 という管理対象がどこにも無い」状態を作れる。

> フロント補足: SPA は最初の 1 回だけ画面一式（HTML+JS+CSS）を受け取り、以降は画面遷移してもサーバーへ取りに行かない。
> ただし「中身のデータ（投稿一覧やログイン）」は都度 `/api/...` でバックエンドに取りに行く。だから配信とデータ処理を分けられる。

## リクエストの流れ（番号順）

```
                          ┌──────────┐
                          │ ユーザー  │
                          └────┬─────┘
                               │ ① https でアクセス
                               ▼
                ┌────────────────────────────────┐
                │         CloudFront              │  ← 一番外の入口（受付の総合窓口）
                └───────┬───────────────┬─────────┘
              ②-A 画面表示 │               │ ②-B データ取得
                URL が「/」 │               │ URL が「/api/*」
                          ▼               ▼
                    ┌──────────┐    ┌──────────┐
                    │   S3     │    │   ALB    │  ③ 生きてるタスクへ振り分け
                    │ (React)  │    │ (受付係) │
                    └──────────┘    └────┬─────┘
                                         │ ④
                                         ▼
                                   ┌──────────────────┐
                                   │  ECS Fargate     │  Spring Boot を実行
                                   └───┬──────────┬───┘
                                ⑤ データ │          │ ⑥ 画像
                                       ▼          ▼
                                  ┌────────┐  ┌──────────┐
                                  │  RDS   │  │ S3(画像) │
                                  └────────┘  └──────────┘
```

| 番号 | 何が起きるか |
|------|------------|
| ① | ユーザーがアクセス。通信は必ず CloudFront に届く |
| ②-A | URL が `/`（画面）なら CloudFront は S3 の React ファイルを返す（最初の1回だけ） |
| ②-B | URL が `/api/*`（データ）なら CloudFront は ALB へ転送する |
| ③ | ALB が生きている Fargate タスクへ振り分ける |
| ④ | Fargate 上の Spring Boot が処理する |
| ⑤ | DB の読み書きは RDS に対して行う |
| ⑥ | 画像の保存・取得は S3 に対して行う |

## コンテナの考え方（Docker / ECR / Fargate）

「EC2 を使わずにバックエンドを動かす」中心の仕組み。3 つの役割を分けて理解する。

| 名前 | 役割 | たとえ |
|------|------|--------|
| Docker イメージ | 動かすのに必要なものを固めた「箱」そのもの | 中身を詰めたお弁当箱 🍱 |
| ECR | 作った箱を AWS に預ける倉庫 | 箱の保管庫 |
| ECS Fargate | 倉庫の箱を取り出して起動し続ける実行係 | 弁当を温めて出し続ける店員＋レンジ |

ポイント: **箱なのは Docker イメージの方**で、**Fargate は箱ではなく「箱を動かす場所」**。役割が別物。
保存先も紛らわしいが、**渡す（保存する）先は ECS ではなく ECR**。ECS は「どの箱を何個どう動かすか」の司令塔、
Fargate はその実行方式（EC2 を使わない）。

### backend の Docker イメージに入れるもの / 入れないもの

```
backend イメージ = ┌─────────────────────────────┐
                  │ ① JRE（Java 実行環境）        │ ← Spring Boot を動かすのに必須
                  │ ② app.jar                    │ ← 自分のコード・SQL・依存が固まった成果物
                  │ ③ 起動コマンド java -jar      │ ← 起動時に何を実行するか
                  └─────────────────────────────┘
```

- **イメージには「データ」を入れない**。コンテナは使い捨てで、作り直すと中身が消えるため。
- **DB・画像のデータは外部（RDS・S3）に永続化**し、接続先やパスワードは起動時に環境変数 / SSM で外から差し込む。
- **1 イメージ = 1 アプリ**。DB（postgres）とバックエンドは別の箱。AWS では DB は箱にせず RDS を使う。

### デプロイの流れ（イメージの一生）

```
backend の Docker イメージを作る（Dockerfile）
        │ ① push（預ける）
        ▼
   ECR（倉庫に保管）
        │ ② ECS が「あの箱を1個動かして」と指示
        ▼
   ECS Fargate（実際に起動・EC2無し） ─接続→ RDS（データ）/ S3（画像）
```

> ローカルとの対比: ローカルでは DB だけを Docker(postgres) で動かし、バックエンドは Mac で直接起動している。
> AWS では バックエンド → ECR/Fargate、DB → RDS に分かれる。RDS は Docker 不要で、
> Terraform で「db.t3.micro の PostgreSQL を 1 台」と宣言するだけで AWS が用意する。

## ALB の役割（受付係）

ALB（Application Load Balancer）は「外から来たリクエストを受け取り、後ろの Fargate タスクへ振り分ける受付係」。

| 役割 | 内容 |
|------|------|
| ① 負荷分散 | タスクを複数に増やしたとき、リクエストを均等に配る |
| ② 宛先の固定 | 使い捨ての Fargate タスクは IP が毎回変わる。ALB が間に立つと CloudFront は「変わらない ALB」だけ知ればよく、裏のタスク入れ替えを吸収できる |
| ③ HTTPS 終端 | 暗号化通信を ACM 証明書で受ける |
| ④ ヘルスチェック | 定期的に `/actuator/health` を叩き、死んだタスクには振り分けない |
| ⑤ 直アクセス遮断 | CloudFront のカスタムヘッダ（合言葉）を検証し、CloudFront 経由のみ通す |

② と ④ は Fargate を安定運用するうえでほぼ必須のため、ECS Fargate + ALB は定番の組み合わせ。

## なぜ CloudFront を「単一の入口」にするのか

フロント（S3）と API（ALB）を別ドメインに分けず、CloudFront 一つにまとめる理由:

- リフレッシュトークンが `HttpOnly` + `SameSite=Lax` Cookie。`SameSite=Lax` は同一サイトでしか送られないため、
  フロントと API を別ドメインに分けると Cookie が送られず**トークンリフレッシュが壊れる**。
- フロントの axios は `baseURL: '/api'`（相対パス）。単一オリジンならそのまま動き、**フロント無改修**で済む。
- 同一オリジンなので **CORS / プリフライトが実質不要**になる。

## 用語の早見表

| 名前 | 一言で |
|------|--------|
| CloudFront | 受付の総合窓口（入口・CDN・HTTPS） |
| S3（フロント） | フロントの倉庫（静的ファイル置き場） |
| ALB | API の案内係（受付・振り分け） |
| ECR | 箱の倉庫（Docker イメージ保管） |
| ECS Fargate | バックエンドを動かす場所（EC2 無し） |
| RDS | データの保管庫（DB） |
| S3（画像） | 画像の倉庫 |
| SSM Parameter Store | 機密値（パスワード等）の金庫 |
